## Body (verified from raw ELF bytes)

```
subu a0,a0,a2      ; a0 = a - c
subu a1,a1,a3      ; a1 = b - d
subu v0,t0,a2      ; v0 = e - c
subu t1,t1,a3      ; t1 = f - d
mult v0,v0,a1      ; v0 = (e-c)*(b-d)
mult t1,t1,a0      ; t1 = (f-d)*(a-c)
subu v0,v0,t1      ; v0 = (e-c)*(b-d) - (f-d)*(a-c)
jr   ra
  slti v0,v0,0
```

Args 5/6 arrive in `t0`/`t1` (EGC passes 5th/6th int args in caller-saved
t0/t1; the matched caller func_00206978 emits `li t0,...; jal; li t1,...`
byte-for-byte). Returns 1 iff the point (a,b) is on the clockwise side of the
directed line (c,d)->(e,f): cross((B-A),(P-A)) < 0. ~30 call sites in
0x2069xx-0x207xxx menu handlers, each with four hardcoded coordinates.

## EE `mult rd,rs,rt` (funct 0x18) — decoding note

Words 0x00451018 / 0x01244818 have R-type funct 0x18, which is UNDEFINED in
stock MIPS32/64 (stock `mult` is funct 0x01 and takes 2 operands into
LO/HI). The EE adds a 3-operand register multiply: `mult RD,RS,RT` =
signed 32x32, RD = low 32 of the product (also updates LO/HI) — see
`data/languages/eecore.sinc:49` in the Emotion Engine Reloaded plugin
(`fct=24` decimal = 0x18). spimdis and Ghidra both print it as a 3-operand
`mult`; plain MIPS objdump/assemblers reject or misread it. Any candidate
containing an EE multiply must be judged by raw bytes / the EER disassembly,
not by stock-MIPS intuition. This is why a "normal" `int` product in C maps
straight onto it.

## Candidate C and the two EGC tie-breaks

Form that reproduces everything except the subu order:

```cpp
extern "C" int func_00208818(int a, int b, int c, int d, int e, int f) {
    int x = a - c;
    int y = b - d;
    int r = (e - c) * y - (f - d) * x;
    if (r < 0)
        return 1;
    return 0;
}
```

EGC v2.73a (-G8 -O2 -ffast-math -fno-exceptions) output for this form:
identical registers, identical mults, identical final `subu v0,v0,t1; jr ra;
slti v0,v0,0` (0x24 bytes), but the four independent subus come out
`[e-c, f-d, a-c, b-d]` (v0, t1, a0, a1) instead of the original
`[a-c, b-d, e-c, f-d]` (a0, a1, v0, t1).

Findings from this session (2026-09-06), extending the 2026-09-04 attempt:

1. The 2026-09-04 note's second diff ('< 0' -> `srl v0,v0,31`) is avoidable:
   the comparison must be the *conditional-return* shape
   `if (r < 0) return 1; return 0;`. In this EGC `return expr < 0;` and
   `return expr < 0 ? 1 : 0;` both compile the zero-test as `srl v0,v0,31`
   (plus a trailing nop, 0x28 bytes), while the if/return-1/return-0 shape
   emits `slti v0,v0,0` in the `jr ra` delay slot, exactly like the original
   (verified on a standalone 1-arg probe: `if (x<0) return 1; return 0;`
   -> `jr ra; slti v0,a0,0`). So only the subu order remains.

2. The original subu order IS reproducible with this very compiler by
   compiling the form above with `-fno-schedule-insns` (pre-RA scheduler
   off, post-RA on): all nine words match the original exactly. So the
   residual diff is purely the pre-RA scheduler's tie-break on four
   independent subus; ~150 statement/paren/temp permutations with the
   project flags never produce [a0,a1,v0,t1] (observed orders are only
   [3,4,1,2], [1,3,4,2], [4,3,1,2], [4,3,2,1], [3,4,2,1] in 1-based
   expansion order, for inline, named-temp, product-temp and r-=q shapes).

3. The original binary was NOT built with the pre-RA scheduler off: adding
   `-fno-schedule-insns` to COMMON_COMPILE_FLAGS and doing a full clean
   build breaks parity in 989snd/ee/989snd.c — 3647 differing bytes, first
   in already-matched `snd_StartSoundSystem` (vram 0x12DA28+, diff starts
   ~0x12DB88). Since matched C elsewhere is generated by the default
   scheduler, Insomniac's build used the default scheduling, and this
   function's subu order is a toolchain tie-break our EGC build resolves
   differently (same class as readBufEndGet / Hud_HeapReset).

## Do not retry blindly

- Do not add `-fno-schedule-insns` globally: it breaks snd_StartSoundSystem
  (and may break others further along in 989snd).
- Do not chase the subu order with more statement permutations under the
  project flags: the expansion order of the four differences is pinned by
  the pinned operand orders (MUL1 = (e-c)*(b-d) with (e-c) first —
  `mult v0,v0,a1`; MUL2 = (f-d)*(a-c) with (f-d) first — `mult t1,t1,a0`;
  subtraction MUL1-MUL2 — `subu v0,v0,t1`; zero-test `< 0` in conditional
  return — `slti v0,v0,0`), which leaves only scheduler-controlled
  permutations of four independent insns.
- If the EGC toolchain is ever swapped/upgraded, retest the candidate above
  as the first thing.
